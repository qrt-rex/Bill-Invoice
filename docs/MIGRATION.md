# bill.rexera.in: PHP to React migration

What the legacy PHP app did, where each piece lives now, how the data moves, and how to cut
over without losing anything. The PHP app in `public_html/` is left untouched until the
new one is verified.

## 1. What the PHP app is

- ~30 PHP pages under `public_html/`, each doing its own SQL and HTML. `updated/` and
  `deploy_to_hostinger/` are byte-identical copies of root files.
- MySQL database `u417368936_bill` on Hostinger. No dump or schema file exists in the
  repo; the schema below was reconstructed from every query in the code.
- Session login (`index.php` / `login.php`) against its own `users` table. Roles in use:
  `admin` (also granted to `super admin`, `admin member`, `manager`) and everything else
  (`user`). One account, `yashkairavi@rexera.co.in`, was hard-coded to see tax invoices
  only and never delete.
- Three branches in `config.php` (AM1 Ahmedabad(Y), AM2 Ahmedabad(A), BRD Baroda), each
  with its own tax-invoice series.

### Problems found (fixed by the rebuild, not carried over)

| Problem | Where |
|---|---|
| Database passwords in plain text in five files, one of them also the CRM database's | `db*.php`, `ajax_fetch_gst_from_crm.php` |
| Some user passwords stored and compared in plain text | `login.php` (`password` column) |
| Invoice editing unlocked by a shared password (`Prakruti`) with no login check | `edit_invoice.php` |
| Any signed-in user could open any invoice by id | `view_invoice.php` |
| `display_errors` on in production, SQL errors echoed to users | most pages |
| State-changing actions on GET links (delete user, delete invoice, reject) with no CSRF protection | `admin.php` |
| Approved requests became tax invoices with no GST breakdown or HSN | `approve_invoice.php` |
| Totals were computed in the browser and trusted by the server | `generate_invoice.php` |
| Invoice number taken from the form, so two people could get the same one | `invoice.php` |
| `create_user.php` still deployed, creates an admin with a known password | `create_user.php` |
| `generate_invoice.php` binds an undefined `$user_id`, so "generated by" is lost | `generate_invoice.php:87` |

Business rules kept exactly (see `backend/app/rules.py`, covered by tests):

- Tax invoice number `Inv{FY}/{PREFIX}-{NNNN}`, next = highest in either the current or the
  old `Invoice-{yy-yy}/{PREFIX}-` format + 1, skipping any number already taken. Proforma
  number `INV-{NNN}` from the latest proforma.
- GST: none unless "Apply GST" and a state are chosen; Gujarat gets CGST 9% + SGST 9%,
  every other state IGST 18%. Particulars/HSN default to "Consultancy Services" / 998312 and
  are fixed on the form except for admins and approved requests (as in `invoice.php`).
- Editing changes item rates only and recomputes tax at the invoice's existing rates.
- Only tax invoices can be deleted; proformas cannot.
- Branch of legacy rows is resolved the way `view_invoice.php` did (stored branch, then the
  invoice number's series).

Deliberate changes, each for a stated reason:

- The financial year of a new tax invoice comes from its invoice date, not today's date, so a
  back-dated invoice lands in the correct GST series.
- Totals, tax and the invoice number are computed on the server when saving.
- Sales users see only invoices, requests and quotations they created.
- The accountant role replaces the hard-coded email; it keeps that account's limits (tax
  invoices only, no delete) and no longer includes user management.
- Bulk export is one printable page (Save as PDF) instead of a ZIP of PNG screenshots.

## 3. Database

A new, separate database (`DATABASE_URL` of the billing API). The main application's
database is never read or written.

| Legacy MySQL table | New table | Notes |
|---|---|---|
| `users` | `billing_users` | Only email, name, job role, billing role, branch. No passwords. |
| `invoices` | `invoices` | Same columns; `client_state_code` -> `client_state`; `billing_contact` merged into `billing_phone`; `invoice_branch` -> `branch_key`; `generated_by_user_id` -> creator email + name. |
| `invoice_items` | `invoice_items` | `particulars`/`description` and `amount`/`total` merged (the approve flow wrote the second pair); `mrp` -> `rate`. |
| `invoice_requests`, `invoice_request_items` | same names | `approved_by_user_id` -> `reviewed_by_email`. |
| `quotations`, `quotation_services` | same names | `total_amount_without_gst` -> `total_amount`, `advance_amount` -> `amount`. |
| `resources` + files in `uploads/` | `documents` | File bytes stored in the database, so they survive redeploys and are in DB backups. |
| `invoice_a` | not migrated | Written only by the unused `g_invoice.php`. The script reports its row count for review. |
| (new) | `payments`, `branches`, `settings`, `audit_logs` | |

Ids of invoices, requests, quotations and documents are preserved.

Migrated invoices are marked `payment_tracked = false`: the PHP app never recorded payments,
so they are left out of Outstanding until someone records a payment against one.

## 4. Data migration runbook

Never point the script at the live database first, and never delete the old one until step 8.

1. Back up: in hPanel, export `u417368936_bill` (phpMyAdmin > Export > SQL). Download the
   `public_html/uploads/` folder too. Keep both off the server.
2. Restore the dump into a local MySQL (`docker run -e MYSQL_ROOT_PASSWORD=x -p 3306:3306 mysql:8`
   then import).
3. Create an empty billing database (PostgreSQL) and set `DATABASE_URL` in `backend/.env`.
4. Dry run (copies, verifies, rolls back):
   ```
   python migrate_from_php.py --source "mysql+pymysql://root:x@127.0.0.1:3306/u417368936_bill" --uploads-dir ./uploads --dry-run
   ```
   It prints and saves a JSON report: row counts and grand-total sums compared source vs
   target, plus anything that needs a person. It stops with BLOCKING if invoice numbers are
   duplicated or empty, a date or type is invalid, or any count does not match.
5. Resolve blocking items in the restored copy, repeat 4 until clean. Read every WARNING:
   users without an email (they need a main-app account), orphan items, `invoice_a` rows,
   missing upload files, items that do not add up to a stored sub-total.
6. Run without `--dry-run` against a staging billing database. Open the staging site and
   check: a sample of invoices against the old `view_invoice.php` side by side, the next
   invoice number per branch, the reports month totals against a phpMyAdmin SUM, documents
   download, every role signs in.
7. Freeze the PHP app (step 4 of cutover below), take a fresh dump, and run steps 2 to 6
   against production.
8. After a month of normal use, archive the old database dump and then drop it: it holds
   plain-text passwords.

## 5. Hosting and cutover

The Hostinger `public_html` plan runs Apache + PHP + MySQL. It can serve the React build as
static files (with the included `.htaccess` for SPA routes and HTTPS), but not a Python API.
The main app's API already runs on Render, so the billing API goes there too.

```
bill.rexera.in       Hostinger, static React build (frontend/dist)
api.bill.rexera.in   Render web service (backend), HTTPS
billing database     New PostgreSQL database (Supabase project or Render Postgres), separate from the CRM's
```

Backend environment (Render): `DATABASE_URL`, `MAIN_API_URL` (the main API's public URL),
`CORS_ORIGINS=["https://bill.rexera.in"]`. Start command:
`uvicorn app.main:app --host 0.0.0.0 --port $PORT`.

Frontend build (`frontend/.env.production`): `VITE_BILLING_API_URL=https://api.bill.rexera.in`,
`VITE_AUTH_API_URL=<main API URL>`, `VITE_MAIN_APP_URL=<main app URL>`. These are public
URLs only; nothing secret goes in the frontend.

Cutover:

1. Deploy the API and a staging frontend (e.g. `billing-staging.rexera.in`) against a staging
   database; run migration step 6.
2. Grant billing roles in Settings > Users; make sure each person has a main-app account.
3. Announce a short freeze.
4. Put the PHP app in read-only mode (rename `public_html/index.php` and `login.php` so no one
   can sign in) and take the final dump.
5. Run the production migration (runbook 7).
6. Move the PHP files to `public_html_legacy/` (not deleted) and upload `frontend/dist/*`
   into `public_html/`.
7. Verify `https://bill.rexera.in` end to end. Rollback = move `public_html_legacy/` back.
